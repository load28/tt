# TASK-060: 에디터 타입 진단이 워크스페이스 `tsconfig.json`을 반영할지 검토

- **완료일**: 2026-08-24

## 목적

`editors/vscode/server/src/tsproject.ts`의 `COMPILER_OPTIONS`는 하드코딩이다
(`target: ESNext`, `lib` 미지정, `strict` 미설정, 워크스페이스
`tsconfig.json` 미참조). 프로젝트가 `lib`·`strict`·`paths` 등을 설정해도
에디터 진단은 그것을 모른다. 이 격차를 좁힐지, 좁힌다면 어떤 방식으로 할지
결정한다.

TASK-058/059의 후속으로 등록됐다. **다만 이것은 이미 두 번 기각된 방향이므로
(TASK-055 결정 1, TASK-058 결정 3), 구현 태스크가 아니라 판단 태스크다.**

## 범위

- 포함:
  - 격차가 실제로 사용자에게 어떤 증상을 만드는지 실측(거짓 음성 목록).
  - `rlc --types`(`src/main.rs`의 `TYPES_COMPILER_OPTIONS`)와 함께 바꿔야
    하는지, 에디터만 바꿔도 되는지 판단.
  - 하기로 결정되면 그때 구현 범위를 이 문서에 확정.
- 제외:
  - 판단 없이 바로 `ts.findConfigFile`을 붙이는 것.

## 선결 질문 (여기서 답해야 진행 가능)

1. **정본이 무엇인가.** 이 저장소에서 타입 검사의 정본은 `rlc --types`이고,
   그것도 tsconfig를 읽지 않고 고정 옵션을 데이터로 넘긴다(TASK-040의
   인메모리 타입 설계). 에디터만 tsconfig를 읽으면 "에디터와 `rlc --types`가
   일치해야 한다"는 기준이 **반대 방향으로** 깨진다. 둘 다 바꿔야 한다면
   그것은 인메모리 타입 설계 자체의 재검토다.
2. **지금 격차가 실제로 해를 끼치는가.** 현재 차이는 전부 안전한 방향이다 —
   에디터 `lib`은 프로젝트 `lib`의 상위집합이고 `strict`는 더 느슨하므로,
   생길 수 있는 것은 **놓친 에러(거짓 음성)뿐**이다. TASK-058에서 확인했듯
   이번에 신고된 거짓 양성은 여기서 나올 수 없었다. 실제로 사용자가 겪은
   거짓 음성 사례를 모으는 것이 선행이다.
3. **`paths`는 별건인가.** `paths`/`baseUrl` 미반영은 모듈 해석 문제라
   `lib`/`strict`와 성격이 다르다. TASK-055는 `@rl/std`에 한해 컴파일러
   사본 폴백으로 우회했다. 나머지 경로 별칭이 실제로 문제가 되는지부터
   확인이 필요하다.
4. **비용.** tsconfig 탐색·`extends` 확장·프로젝트별 캐시 무효화·다중
   tsconfig(모노레포)를 언어 서버가 떠안게 된다. TASK-055가 기각한 사유가
   그대로 유효한지 재확인.

## 의사결정

### 결정 1: 별도 구현 없이 후속 네이티브 백엔드 작업으로 완료 처리한다

- **상황**: 이 태스크가 지적한 `editors/vscode/server/src/tsproject.ts`의 고정
  옵션 경로는 TASK-074에서 제거됐다. 현재 에디터는 TASK-086·087의 공통
  엔진을 사용하고, 엔진은 명시된 `--project` 또는 입력 위 가장 가까운
  `tsconfig.json`을 프로젝트 정체성으로 삼는다.
- **검토한 대안**:
  - A. 태스크를 계속 `대기`로 둔다 — 이미 사라진 구현을 대상으로 한 작업이
    남아 INDEX가 현재 구조와 어긋난다.
  - B. `취소`한다 — `tsconfig.json` 반영 여부를 검토만 하고 기각한 것이
    아니라, 후속 작업이 더 일반적인 프로젝트 그래프로 요구를 구현했으므로
    사실과 다르다.
  - C. 후속 구현 근거를 기록하고 `완료`한다.
- **선택과 근거**: C. `src/engine/mod.rs::identity_of`는 명시된 설정이나 가장
  가까운 `tsconfig.json`을 선택한다. `src/typescript/host.mjs`는 그 설정으로
  TypeScript 프로젝트를 열며, 에디터 엔진 테스트는 `strict: true`와
  `include: ["src"]`인 워크스페이스에서 프로젝트 전체 진단을 검증한다.

### 결정 2: CLI와 에디터의 정본은 공통 엔진의 프로젝트 설정이다

- **상황**: 원래 선결 질문은 에디터만 설정을 읽으면 CLI와 진단이 다시
  어긋난다는 것이었다.
- **검토한 대안**: 에디터 전용 설정 해석을 다시 추가 / CLI와 에디터가 함께
  사용하는 엔진의 프로젝트 설정을 유지.
- **선택과 근거**: 후자. TASK-086의 `Engine`과 TASK-087의 LSP 어댑터 전환으로
  양쪽이 같은 `(tsconfig, root)` 프로젝트 정체성과 TypeScript 백엔드를
  사용한다. 따라서 `extends`·`paths`·`lib`·`strict` 해석은 별도 복제가
  아니라 TypeScript 프로젝트가 소유한다.

## 이슈 및 해결

### 이슈 1: 로컬 확장 테스트에 전체 TypeScript 도구 체인이 없다

- **증상**: 기본 확장 테스트는 `ttc not on PATH`로 73건을 건너뛰었다. 빌드된
  `target/debug/ttc`만 PATH에 추가하면 `tsgo`가 필요한 테스트는 계속
  건너뛰고 typed-check 테스트 2건은 빈 진단으로 실패했다.
- **원인**: 현재 셸에는 `ttc`와 함께 사용할 `tsgo` 실행 파일이 없다. 컴파일러
  하나만 강제로 노출한 실행은 확장 테스트가 요구하는 도구 체인을 완성하지
  않는다.
- **해결**: 저장소의 표준 확장 테스트 명령을 도구 탐지 상태 그대로 실행해
  지원되는 skip 계약과 실패 0건을 확인했다. 프로젝트 설정 계약 자체는 실제
  `tsconfig.json` 픽스처를 쓰는 테스트 소스와 Rust 엔진/네이티브 테스트로
  함께 확인했다.
