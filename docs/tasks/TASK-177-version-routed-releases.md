## 목적

`Cargo.toml` 버전 변경을 단일 배포 트리거로 사용하되 개발 선행 버전과 정식
버전을 서로 다른 배포 채널로 안전하게 분기한다. 첫 npm 개발 배포에서 확인된
레지스트리 차단 원인도 재현 가능한 형태로 기록한다.

## 범위

- 포함: `-dev.N` 증가 감지, 동일 버전 건너뛰기, 정식 버전의 production 분기,
  버전 파생 테스트와 기여 문서 갱신
- 제외: npm 스팸 탐지 정책 우회, npm 지원팀의 패키지 이름 차단 해제

## 의사결정

### 결정 1: `Cargo.toml` 버전이 배포 채널까지 표현

- **상황**: 코드가 push될 때마다 배포하지 않으면서 `0.3.0-dev.1` 같은 명시적
  개발 버전 증가와 `0.3.1` 같은 정식 버전 증가를 구분해야 한다.
- **검토한 대안**: 별도 개발 버전 파일은 정식 버전과 기준 버전이 어긋날 수 있다.
  모든 push에 타임스탬프만 붙이면 배포 의도를 표현하지 못한다. Cargo 버전의
  SemVer 선행 버전을 쓰면 한 값으로 버전과 채널을 모두 표현할 수 있다.
- **선택과 근거**: `Cargo.toml`의 `X.Y.Z-dev.N`은 development, `X.Y.Z`는
  production으로 분류한다. 직전 커밋과 값이 같으면 어떤 배포도 하지 않는다.

### 결정 2: 실제 npm 버전에는 실행 고유 접미사를 유지

- **상황**: 같은 개발 기준 버전의 수동 재실행과 Actions 재시도도 npm의 불변
  버전 제약을 만족해야 한다.
- **검토한 대안**: `X.Y.Z-dev.N`을 그대로 게시하면 한 번 실패한 실행의 재시도가
  같은 버전을 덮어쓸 수 없다. 날짜·시간만 쓰면 같은 초의 재시도를 구분하지
  못한다.
- **선택과 근거**: 기준 선행 버전 뒤에 UTC 날짜·시간과 run/attempt를 붙인다.

## 이슈 및 해결

### 이슈 1: Windows 플랫폼 패키지 이름이 npm 스팸 탐지에 차단됨

- **증상**: `npm publish`가 `tt-lang-win32-x64`에서 `403 Forbidden`과
  `Package name triggered spam detection`을 반환했다. 앞선 네 패키지는 같은
  토큰으로 정상 게시됐다.
- **원인**: 인증이나 권한이 아니라 npm 레지스트리의 패키지 이름 정책 차단이다.
- **해결**: 자동화가 오류를 숨기지 않도록 유지한다. 현재 이름을 유지하려면 npm
  지원팀의 차단 해제가 필요하며, 이 외부 조치는 이 태스크 범위에서 제외한다.

## 결과

`Cargo.toml` 버전이 같으면 배포하지 않는다. `X.Y.Z-dev.N` 증가 시 timestamp가
붙은 npm `dev` 패키지와 GitHub VSIX pre-release를 배포하고, `X.Y.Z` 증가 시
production npm 패키지와 GitHub Release를 배포한다. npm이 차단한
`tt-lang-win32-x64` 이름은 지원팀의 해제가 필요하다.
