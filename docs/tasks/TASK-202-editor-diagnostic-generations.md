## 목적

한 문서의 빠른 진단과 typed 진단이 따로 발행되면서, 독립적인 오류가 편집 중 잠시
사라졌다가 다시 나타나는 현상을 없앤다.

## 범위

- 포함: 문서 버전별 진단 조정, 원자적 발행, 오래된 결과 거부, LSP 버전 전달,
  시간 순서 회귀 테스트
- 제외: 진단 문안·규칙 변경, 컴파일러 의미 분석 변경, pull diagnostics 전환

## 의사결정

### 결정 1: 한 문서 버전의 활성 진단 계층을 한 번에 발행한다

- **상황**: `publishDiagnostics`는 파일의 진단 목록 전체를 교체한다. 현재 서버는
  빠른 결과를 먼저 발행하고 같은 버전의 typed 결과를 나중에 합쳐 재발행하므로,
  이전 버전의 typed 오류가 중간 목록에서 빠진다.
- **검토한 대안**: 이전 typed 범위를 새 텍스트에 재투영하면 빠른 발행은 유지할 수
  있지만 모든 LSP 편집 형태에 대한 범위 변환 계약이 추가된다. 현 구조를 유지하면
  깜빡임을 고칠 수 없다. 활성 계층을 모두 기다리면 발행은 typed 검사만큼 늦지만
  이전 진단은 그동안 에디터가 유지하며 범위도 직접 추적한다.
- **선택과 근거**: 빠른 검사·TypeScript 서비스·typed compiler·hint 결과를 같은
  문서 버전의 하나의 세대로 모으고, 모두 완료된 뒤 한 번만 발행한다. 결과 좌표와
  구성 요소가 같은 버전에 속한다는 단순한 계약을 얻는다.

### 결정 2: 발행 알림에도 문서 버전을 싣는다

- **상황**: 서버는 내부에서 오래된 비동기 결과를 버리지만 LSP 알림에는 버전을
  보내지 않아 클라이언트가 결과의 문서 세대를 확인할 수 없다.
- **검토한 대안**: 서버 내부 검사만 유지할 수 있지만 전송 이후 문서 변경과 알림
  처리 사이의 순서를 클라이언트가 판정할 수 없다.
- **선택과 근거**: `PublishDiagnosticsParams.version`에 검사한 문서 버전을 넣어
  서버와 클라이언트가 같은 세대 계약을 공유하게 한다.

## 이슈 및 해결

### 이슈 1: 새 버전의 첫 알림에서 typed 오류가 누락됨

- **증상**: 오류 A와 typed 오류 B가 함께 있는 파일에서 A를 고치면 B가 잠시
  사라졌다가 다시 나타났다.
- **원인**: `publishDiagnostics`가 전체 목록을 교체하는데, 빠른 결과는 새 버전의
  typed 결과가 없다는 이유로 B를 제외해 먼저 발행하고 typed 검사가 끝난 뒤
  다시 B를 합쳐 발행했다.
- **해결**: 결정 1에 따라 같은 validation generation의 모든 활성 계층이
  끝난 뒤에만 전체 목록을 발행했다. 문서 버전 외에 단조 증가 generation도
  검사해 설정 변경처럼 같은 문서 버전에서 겹치는 오래된 실행도 버렸다.

### 이슈 2: 로컬 확장 전체 테스트의 기존 환경 의존 실패

- **증상**: 실제 로컬 typescript-go를 연결한 확장 전체 테스트에서 112개 중
  105개가 통과하고 7개가 실패했다. 실패는 `/var`와 `/private/var` 경로 차이,
  completion 기대 차이, 기존 sidecar 실패 판정이었다. 새 진단 회귀 테스트를
  포함한 `server.test.js` 15개는 모두 통과했다.
- **원인**: 실패한 테스트는 변경한 진단 조정 경로를 통과하지 않으며, 현재 로컬
  typescript-go와 macOS 임시 경로 환경에 대한 기존 테스트 기대와 달랐다.
- **해결**: 범위를 확장해 별도 기능을 변경하지 않았다. 이번 경로는 실제 도구를
  사용한 `server.test.js` 전체와 필수 저장소 게이트로 검증했다.
