## 의사결정

### 결정 1: RC에서 릴리스 브랜치를 시작한다

- **상황**: Beta와 RC가 각각 준비·검증 단계를 요구해 현재 프로젝트 규모에 비해 단계가 많다.
- **검토한 대안**: Beta 유지 / RC 제거 / Beta 제거.
- **선택과 근거**: 사전 검증 단계인 RC는 유지하고 Beta를 제거한다. RC 실행 시 최신 `main`에서
  `release-X.Y`를 만들며 이후 최신 `main` 전체를 자동 동기화하지 않는다.

### 결정 2: 일반적인 SemVer 승격 순서를 사용한다

- **상황**: TypeScript의 `X.Y.0-beta → X.Y.1-rc → X.Y.2` 규칙은 Beta 제거 후 불필요한
  patch 번호 공백을 만든다.
- **검토한 대안**: 기존 번호 유지 / `X.Y.0-rc → X.Y.0 → X.Y.1` 사용.
- **선택과 근거**: RC와 Stable이 같은 기반 버전임을 드러내는
  `X.Y.0-rc → X.Y.0 → X.Y.1`을 사용한다.

### 결정 3: TypeScript처럼 Nightly만 자동 게시한다

- **상황**: TypeScript와 같은 자동화 범위를 적용하되 정식 릴리스의 의도적 승격을 보존해야 한다.
- **검토한 대안**: 모든 게시 수동 / 모든 게시 자동 / Nightly 자동·정식 릴리스 수동.
- **선택과 근거**: 예약된 `main` 빌드는 npm `next`로 자동 게시한다. RC·Stable·Patch는
  TypeScript의 `trigger: none` 게시 파이프라인처럼 성공한 빌드 산출물을 수동 승격한다.
