## 목적

GitHub Discussion에서 관점이 다른 에이전트들이 충분히 논증하고 상대 의견에 따라
입장을 수정하며, 합의 또는 사람의 최종 판단에 도달하는 셀프 호스팅 봇을 만든다.

## 범위

- 포함: Discussion 웹훅, GitHub App 인증, Codex CLI 호출, 라운드 진행, 멘션 응답,
  합의·교착 판정, 로컬 실행 문서와 테스트
- 제외: 저장소 코드 수정 권한, 사람 대신 최종 결정을 강제하는 기능, 외부 호스팅 배포

## 의사결정

### 결정 1: 중앙 오케스트레이터가 공개 토론 라운드를 소유한다

- **상황**: 여러 GitHub App이 서로의 댓글 웹훅에 직접 반응하면 중복 실행과 무한
  응답을 막으면서 토론 순서를 보장하기 어렵다.
- **검토한 대안**: 각 App의 독립 반응 / 단일 App 안의 비공개 토론 / 중앙
  오케스트레이터가 여러 App 신원으로 공개 발언
- **선택과 근거**: 중앙 오케스트레이터가 각 App의 발언 순서와 종료 판정을 맡는다.
  공개 토론을 유지하면서 한 Discussion에 하나의 결정 상태를 보장할 수 있다.

### 결정 2: 입장 변경을 명시적인 숙의 결과로 모델링한다

- **상황**: 에이전트가 자기 주장만 반복하거나 근거 없이 쉽게 동의하지 않게 해야 한다.
- **검토한 대안**: 자유 형식 댓글 / 찬반 투표 / 구조화된 입장 변화와 반대 근거
- **선택과 근거**: 상대 주장 요약, 동의점, 반박점, 입장 변화, 변화 근거와 중대한
  반대를 구조화해 받는다. 납득과 고수 모두 근거를 남길 수 있다.

### 결정 3: 공개 웹훅은 Tailscale Funnel로 전달한다

- **상황**: 로컬 오케스트레이터가 GitHub의 공개 웹훅을 받아야 한다.
- **검토한 대안**: ngrok / 고정 역방향 프록시 / Tailscale Funnel
- **선택과 근거**: 이미 설치된 Tailscale을 사용하고 Funnel이 HTTPS 종단과 백그라운드
  설정을 관리하게 한다.

### 결정 4: 이벤트 수신은 저장소 Webhook이 담당한다

- **상황**: 진행자 GitHub App 설정 화면이 Webhook URL과 활성 상태를 보존하지 않았다.
- **검토한 대안**: 진행자 App 재생성 / GitHub App Webhook 반복 설정 / 저장소 Webhook
- **선택과 근거**: 봇 발언 신원과 권한은 기존 GitHub Apps를 유지하고, 이벤트 수신만
  `load28/tt` 저장소 Webhook으로 분리했다. 동일한 HMAC 서명 검증을 사용하면서
  `discussion`과 `discussion_comment` 이벤트만 전달할 수 있다.

## 이슈 및 해결

- Funnel 활성화 직후 공개 DNS가 생성되지 않았다. 임시 디렉터리에서 HTTPS 인증서
  발급을 요청해 DNS 생성을 완료하고 임시 인증서와 개인키를 삭제했다.
- 진행자 GitHub App의 Webhook 설정이 저장되지 않았다. 저장소 Webhook으로 이벤트
  수신을 분리하고 GitHub Apps는 댓글 작성 신원으로 유지했다.
