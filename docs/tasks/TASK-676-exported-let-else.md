## Purpose

`export const Full(value: v) = b else { throw new Error("empty"); };`
failed with `error[lowering-plan-failed]: tt host lowering could not plan
this construct: the generated TypeScript for it does not parse: Expected
',', got ';'`, although a let-else is allowed at a module's top level
(`docs/ai/tt.md`, "let-else") and TypeScript exports any declaration
written after `export`.

- Excluded: related information for a variant constructor's missing

## Decisions

### Decision 1: The let-else owns its `export` modifier and exports the declaration it emits

- **Context**: The parser claimed the statement from its `const`, leaving
  `export ` as verbatim text before it. The host projection writes a
  statement decision as one block (`{ $tt_syntax_stmt_N; (b); if (true)
  {...} }`), so the projection read `export { ... }` as an export clause
  and stopped at a generated byte, which is reported as a lowering
  failure. Codegen would have exported the generated temporary instead of
  the bindings.
- **Alternatives considered**:
  - Leave `export` verbatim and project an exported let-else as a
    declaration: the block is what gives the `else` body and the
    initializer's nested constructs their statement region, and the
    decision's host owner would split across two statements.
  - Reject `export` on a let-else: TypeScript exports every declaration
    form, and `const P = x else {...}; export { v };` already works, so
    the rejection would only be a missing feature.
- **Decision and rationale**: As the `try` declaration already does
  (`parse_try_decl`'s owner starts at an `export`/`declare` before the
  keyword), the let-else's owner starts at a directly preceding,
  undotted `export` when the statement is not in a function body (where
  TypeScript accepts no `export`), and `LetElseStmt::exported` flows
  through HIR and Core IR to codegen, which writes `export` before the
  bindings' declaration: `export const { value: v } = $tt_t0;`, after the
  test, as TypeScript's `export` applies to the declaration it precedes
  (ECMAScript `ExportDeclaration : export Declaration`). In a namespace
  the same declaration is a namespace export.

### Decision 2: The projection keeps the file a module

- **Context**: Whether a file is a script is read from the projection's
  top-level module items (`is_script`), and the projection no longer
  holds the `export`, so a file whose only export is a let-else would be
  treated as a script (its storage named after the global it declares,
  `$tt_t0$label`).
- **Decision and rationale**: After an exported let-else's block the
  projection writes `export {};`, the empty export clause that marks a
  module without declaring anything (the statement TypeScript's TS1208
  names: "Add an import, export, or an empty 'export {}' statement to
  make it a module"). Inside a namespace it is an
  empty namespace export, which changes nothing. The case's `only.tt`
  pins the module storage name `$tt_t0`.

## Issues and resolutions

### Issue 1: The first version of the case bound a name in only one alternative

- **Symptom**: `match-or-binding-mismatch` for `Full(value: counter) |
  Empty`.
- **Cause**: The case, not the compiler: every alternative must bind the
  same names.
- **Resolution**: The case uses `Full(value: counter) | Half(value:
  counter)`.

### Issue 2: A missing constructor argument's related place is the variant name

- **Symptom**: `Shape.Circle()` reports TS2554 with "An argument for
  'radius' was not provided" at the variant's name (`Shape`), not at
  `radius: number`.
- **Cause**: The generated constructor writes its parameter names as
  generated text (`push_lit` in `emit_adt`), so TypeScript's related span
  (the parameter declaration) maps to the declaration's anchor.
- **Resolution**: Not changed here. Mapping the parameter name to the
  field's name would also map TypeScript's parameter answers (semantic
  tokens, hover, references on the generated parameter) onto the field,
  beside the property the union's member already maps there; that needs
  its own task with editor cases for each.

### Issue 3: The Rust API baseline was committed without the new field

- **Symptom**: The full gate (recorded in TASK-667) failed
  `public_api::the_rust_api_matches_its_baseline` with `+ pub exported:
  bool,` in `pub struct LetElseStmt` (`ttc::hir`).
- **Cause**: `hir::LetElseStmt` is public API (TASK-648's baseline), and
  the suites run before the commit did not include `public_api`.
- **Resolution**: The baseline is updated in a second TASK-676 commit;
  `git rebase` is not available in this workspace to fold it into the
  first, and the series is squash-merged.
