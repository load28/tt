# TASK-707: Report a statement a `result` block's `}` cuts off as the author's syntax error

- **Status**: Complete
- **Started**: 2026-10-01
- **Completed**: 2026-10-01
- **Commit**: see `git log --grep TASK-707`

## Purpose

TASK-700 (Issue 2) found that `result { return try read(x) + }` reports
`lowering-plan-failed` ("the generated TypeScript for it does not parse:
Expression expected") over the whole block, while `result { const n = try
read(x) *; return n; }` reports `source-not-typescript` at the `;`. Both
are the author's TypeScript not parsing, and TypeScript reports the first
at the `}`. It was the one path to `lowering-plan-failed` the matrix
reached.

## Scope

- Included: the projection of a `result` block's body
  (`ProjectionBuilder::emit_result_region` in
  `src/program_syntax/projection.rs`), a compiler case, the listed defect
  in `tests/oracle-failures.txt` and its matrix baseline, the reason for
  `lowering-plan-failed` in `tests/diagnostic-codes-without-cases.txt`, and
  `docs/ai/tt.md`.
- Excluded: the `lowering-plan-failed` code itself, which stays for the
  internal invariants that report it (Decision 2); `result-no-success-value`
  next to the syntax error when the body has no `return` (a separate fault,
  reported as before).

## Sources

- TypeScript's parser (`src/compiler/parser.ts`, `parseErrorAtCurrentToken`):
  an expression, name, or statement missing before a block's `}` is
  reported at the `}`. With the pinned TypeScript, `tsc --noEmit` reports
  `() => { if (x) }` (TS1109), `() => { return x. }` (TS1003), and
  `() => { l: }` (TS1109) at the `}` (checked in this task).
- `docs/ai/tt.md` (diagnostics): TypeScript that does not parse inside a
  claimed construct, "a `result` block" named, is `source-not-typescript`.
- `src/program_syntax/projection.rs` (`push_source_boundary`, TASK-711): a
  compiler-written delimiter after a copied fragment stands for the source
  token that ends it; a match's block arm is already projected as `{` body
  boundary-`}`.

## Decisions

### Decision 1: Project the body as a block closed by a source boundary

- **Context**: The body was projected straight into the region's function,
  followed by the generated `\nreturn undefined;})()`. A body cut off by
  the `}` therefore made SWC stop inside generated text (at `return`, or at
  `undefined` after `x.` read `return` as a member name), which is
  classified as a broken lowering invariant. Worse, a body ending in a
  statement head that takes a statement (`if (c)`, a label) absorbed the
  generated `return undefined;` as that statement: the projection parsed,
  the TypeScript error was lost, and the build failed later with
  `verify-failed` or not at all.
- **Alternatives considered**: (a) Make the generated `\nreturn undefined;`
  a boundary: it fixes the first two shapes but not the absorbed statement.
  (b) Re-parse the block body as TypeScript statements before lowering: a
  second parse for what the projection parse already decides. (c) Wrap the
  body in `{ ... }` and record the closing `}` as a boundary.
- **Decision and rationale**: (c). A `}` is what ends the body in the
  source, it cannot be absorbed by an incomplete statement, and a stop on
  it maps (TASK-711) to the block's own `}`, where TypeScript reports.
  This is the shape a match's block arm already has, and a `result` with an
  outward jump already projects its body inside `for (;;) { ... }`, so the
  owner model reads a nested block there; the region's `return`s still
  belong to its function. The full `result` case and editor suites pass
  unchanged.

### Decision 2: Keep `lowering-plan-failed` for internal invariants

- **Context**: With this path gone, no known program reports
  `lowering-plan-failed`.
- **Alternatives considered**: Retire it as TASK-708 retires
  `stray-result`: it has reporting sites (`src/verify.rs`, a projection
  that does not parse at a generated byte and an evaluation plan that
  cannot be built), so a future defect would then surface as an unexplained
  internal error.
- **Decision and rationale**: Keep it; its explanation already calls a
  report a gap the compiler has to close. The without-cases list now says
  no known program reports it and why.
