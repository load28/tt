# tt를 만들게 된 이유

[English](./why-tt.md)

몇 년째 타입스크립트를 쓰고 있고, 지금도 좋은 언어라고 생각합니다. 그래서 이
글은 타입스크립트에 대한 불만이라기보다는, 제가 계속 걸려 넘어지던 지점 하나와
결국 거기서 무엇을 하게 됐는지에 대한 기록에 가깝습니다.

## 탈출구는 설계의 일부입니다

타입스크립트의 첫 번째 임무는 이미 존재하는 자바스크립트를 받아들이는 것입니다.
이건 설계의 각주가 아니라 토대입니다. `any`와 `as`가 있는 이유도 여기에 있습니다.
십수 년 동안 돌아가던 코드 위에 얹힌 타입 시스템에는, 증명할 수 없는 부분을
담아둘 자리가 필요하니까요.

대부분은 이 키워드들을 피하는 법을 배웁니다. 그리고 진지하게 피하기 시작하는
순간, 비용이 어디로 옮겨갔는지 보이기 시작합니다. 타입을 위한 타입을 쓰게 되는
것이죠. 조건부 타입, 재귀 튜플 타입, 오버로드 테이블. 타입 레벨 코드가 점점
자라나서, 나중에는 애너테이션 안에 또 하나의 언어가 살고 있는 것처럼 느껴집니다.

제가 자꾸 돌아오게 되는 예는 파이프 연산자입니다. 타입스크립트에는 `|>`가 없으니
라이브러리들은 가변 인자 `pipe(...)`로 흉내를 냅니다. 어느 구현을 열어봐도 모습은
비슷합니다. 인자 개수마다 손으로 쓴 오버로드가 층층이 쌓여 있고, 보통 열 개나
스무 개쯤에서 멈춥니다.

```ts
export function pipe<A, B>(a: A, ab: (a: A) => B): B;
export function pipe<A, B, C>(a: A, ab: (a: A) => B, bc: (b: B) => C): C;
// ...계속, 계속
```

한계에 닿기 전까지는 잘 동작합니다. 마지막 오버로드보다 한 단계만 더 이어붙이면,
그때 받는 에러는 내 코드가 아니라 라이브러리의 오버로드 목록에 대한 이야기입니다.
누구의 잘못도 아닙니다. 만든 사람들은 가능한 최선을 했습니다. 한계는 구조적인
것입니다. 언어에 없는 문법을 타입 시스템으로 *설명*해 달라고 요청하고 있는
것이고, 설명은 결국 실물의 근사치일 수밖에 없습니다.

## 컴파일러는 알고 있지만 말해주지 않습니다

또 하나 마음에 걸렸던 건 침묵이었습니다.

```ts
type Shape =
  | { kind: "circle"; radius: number }
  | { kind: "rect"; width: number; height: number };

function area(shape: Shape) {
  switch (shape.kind) {
    case "circle":
      return Math.PI * shape.radius ** 2;
  }
}
```

타입스크립트는 `shape.kind`가 정확히 `"circle" | "rect"`라는 걸 알고 있습니다.
여기서 `"rect"`가 처리되지 않았다는 것도 알고 있습니다. 정보는 이미 좁혀진 타입
안에 그대로 들어 있습니다. 그런데 물어보지 않으면 알려주지 않고, 물어본다는 건
관용구를 직접 쓴다는 뜻입니다. 값을 `never`에 대입하는 `default` 분기를 두거나,
반환 타입을 명시하고 컴파일러 옵션을 맞춰두거나. 같은 `case`를 두 번 써도
컴파일러는 아무 말도 하지 않습니다. 그건 린트 규칙의 몫으로 남아 있습니다.

타입스크립트가 짊어진 조건들을 생각하면 이 중 무리한 건 하나도 없습니다. 다만
태그드 유니언이 있는 다른 언어들에서 이 검사는 대개 언어의 기능인데, 여기서는
제가 잊지 않고 써야 하는 패턴이라는 점이 계속 남았습니다. 타입 시스템이 입을
열게 만들기 위한, 또 하나의 타입을 위한 타입인 셈이니까요.

## 제가 원했던 것

요구사항은 계속 복잡해지고 기대 수준도 함께 올라갑니다. 코드는 그걸 따라갑니다.
함수 하나가 머릿속에 다 안 들어오는 크기가 되면, 결국 저를 구해주는 건 단순한
것들입니다. 무엇이 들어가고 무엇이 나오는지 분명히 아는 것, 실행되기 전에 최대한
많은 실수를 잡는 것, 그리고 그 모든 걸 세 화면짜리 의식 없이 짧게 쓸 수 있는 것.

동기는 그게 전부입니다. 이 세 가지를 타입스크립트 안에서 갖고 싶었습니다. 타입을
더 영리하게 쓰는 방식이 아니라, 그 일을 한 단계 앞의 컴파일 단계로 옮기는
방식으로요.

## 이미 있는 언어를 쓰지 않은 이유

ReScript 같은 언어들은 이 문제를 이미, 그것도 훌륭하게 풀었습니다. 다만 그
방식이 독자적인 문법을 자바스크립트로 컴파일하는 형태이고, 거기서 허들이
생깁니다. 기능 하나를 도입하는 게 아니라, 적어도 경계에서는 생태계 밖으로 한 발
나가는 일이 되니까요. 이미 쓰고 있는 패키지의 타입, 에디터 도구, 작년에 팀이 쓴
코드, 다음에 합류할 사람. 타입스크립트가 많이 쌓인 코드베이스에서 이 교환은
언어가 아무리 좋아도 정당화하기 어렵습니다.

그사이 타입스크립트는 선택적인 레이어이길 그만뒀습니다. Bun은 타입스크립트를
네이티브로 실행하고, Node에도 타입 스트리핑이 들어왔고, 타입을 먼저 설계하는 API가
기본이 됐습니다. 타입스크립트는 자바스크립트의 슈퍼셋이고, 이제는 생태계에서
빼놓기 어려운 언어가 됐습니다.

그래서 저는 반대 방향으로 갔습니다. tt는 타입스크립트의 슈퍼셋이고, 자바스크립트가
아니라 *타입스크립트로* 컴파일됩니다. 타입스크립트가 계속 타깃이자 타입 검사기이고,
프로젝트의 나머지 도구들이 이미 이해하고 있는 그 언어로 남습니다.

## 나머지가 전부 매달려 있는 하나의 원칙

**모든 유효한 타입스크립트 파일은 유효한 tt 파일이다.**

컴파일러는 자기가 소유한 구문만 변환하고, 나머지는 바이트 단위 그대로
통과시킵니다. 방출되는 결과물은 평범한 타입스크립트입니다. `kind`로 태그된 유니언,
`switch` 문, 보통의 함수. 런타임 라이브러리도 없고 타입 트릭도 없습니다. tt가 할
말이 있으면 파일·행·열과 함께 스스로 말합니다.

이 원칙이 두 가지를 벌어다 줍니다. 우선 tt를 배우는 일이 언어 하나를 배우는 게
아니라 키워드 몇 개를 익히는 일이 됩니다. 그리고 마이그레이션이 프로젝트가 되지
않습니다. 파일 확장자만 바꿔도 그대로 컴파일되니까요. `.tt`와 `.ts`는 양방향으로
서로를 import할 수 있어서, 아예 마이그레이션을 하지 않는 선택지도 있습니다.
중요한 부분 — 상태 기계, 파서, 결제 흐름 — 만 tt로 쓰고 기존 타입스크립트에서 그냥
가져다 쓰면 됩니다.

앞에서 본 `switch`를 tt로 옮기면 이렇습니다.

```tt
enum Shape {
  Circle(radius: number),
  Rect(width: number, height: number),
}

const area = (shape: Shape): number =>
  match (shape) {
    Circle(radius) => Math.PI * radius ** 2,
  };
```

```
ttc: shape.tt:7:3: match on enum Shape is not exhaustive: missing "Rect" (add the missing arms or a final `_` arm)
```

`Circle`을 두 번 쓰면 `match: duplicate arm "Circle"`이 나옵니다. 타입 시스템이
처음부터 갖고 있던 바로 그 정보인데, 이제 소리 내어 말해줄 뿐입니다.

## 시그니처만 보고 읽히는 에러

나머지 절반은 실패입니다. tt는 에러를 던지는 대신 반환하는 쪽에 기대고, 보통
사람들이 그 스타일을 포기하게 만드는 불편함을 문법으로 덜어냅니다.

```tt
const loadProfile = (id: string): TResult<Profile, DbError | HttpError> =>
  result {
    const user <- findUser(id);
    const company <- fetchCompany(user.companyId);
    { user, company }
  };
```

`<-`는 성공 값을 꺼내고 실패면 블록 전체를 그 실패로 끝냅니다. 에러 타입은
내려가면서 알아서 합쳐집니다. 성공 경로처럼 읽히는 이유는 실제로 성공 경로이기
때문이고, 실패는 주석이나 세 프레임 위의 `catch`가 아니라 시그니처에 적혀
있습니다.

tt가 `throw`를 막지는 않습니다. 여전히 타입스크립트이고, 필요할 때 `throw`는
그대로 있습니다. 다만 다른 쪽 스타일을 실제로 쓸 만하게 만들어 둘 뿐입니다.

## 예상하지 못했던 이유 하나

이제 많은 코드가 AI와 함께 쓰입니다. 그게 잘 되느냐를 가르는 건 결국
컨텍스트입니다. 그것도 "충분한" 컨텍스트가 아니라, 모델이 실제로 보고 있는 창
안에 들어오는 *정확한* 컨텍스트입니다.

그런데 그건 제가 저 자신을 위해 원했던 성질과 같은 것이었습니다. `match`는 케이스의
전체 목록이 바로 거기 있습니다. `TResult<Profile, DbError | HttpError>`를 반환하는
시그니처는 실패의 전체 목록이 바로 거기 있습니다. 두 답 모두 다른 파일이나, 몇
프레임 아래의 `throw`나, 누가 회의에서 설명한 관례 속에 숨어 있지 않습니다. tt
코드 마흔 줄을 읽은 모델은 그 마흔 줄이 무슨 일을 하는지 말할 수 있고, 밤 열한
시의 리뷰어도 마찬가지입니다.

## 지금 어디까지 왔나

tt는 아직 초기 단계입니다. 컴파일러는 Rust로 작성돼 있고, 언어는 일곱 구문과
바인딩 수식자 하나 — `enum`, `match`, `try`, `let-else`, `if let`, `|>`(그리고
`flow`), `result` 블록, `val` — 이 전부이며, 아직 프로덕션에 올리라고 권하지는
않습니다.

그래도 모양만큼은 제가 원하던 그대로입니다. 포기할 것은 없고, 배울 것은 몇 개뿐이고,
컴파일러는 타입이 이미 알고 있던 것을 말해줍니다.
