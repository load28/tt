# tt를 만든 이유

[English](./why-tt.md)

저는 여러 해 동안 TypeScript를 사용해 왔고, 지금도 TypeScript를 좋아합니다.
그러니 이 글은 TypeScript에 대한 불평이 아닙니다. 제가 계속 막히곤 했던 한
지점과, 결국 그 문제를 어떻게 풀게 되었는지에 관한 이야기입니다.

## 타입 탈출구는 설계를 떠받치고 있습니다

TypeScript의 첫 번째 임무는 이미 존재하는 JavaScript를 받아들이는 것입니다.
이는 설계의 사소한 각주가 아니라 토대입니다. `any`와 `as`가 존재하는 이유도
같습니다. 십 년 넘게 실행되어 온 코드 위에 타입 시스템을 얹으려면, 증명할 수
없는 부분을 담아 둘 곳이 필요합니다.

대부분의 개발자는 이런 기능을 피하는 법부터 배웁니다. 그런데 이를 정말 엄격하게
피하기 시작하면, 비용이 다른 곳으로 옮겨갔다는 사실이 보입니다. 다른 타입이
제대로 동작하도록 만들기 위한 타입을 쓰게 됩니다. 조건부 타입, 재귀 튜플 타입,
오버로드 목록 같은 것들입니다. 타입 수준의 코드가 점점 불어나면서, 마치 타입
표기 안에 또 하나의 언어가 들어 있는 것처럼 느껴집니다.

제가 계속 떠올리게 되는 예가 파이프 연산자입니다. TypeScript에는 `|>`가 없으므로
라이브러리는 가변 인자 함수인 `pipe(...)`로 이를 흉내 냅니다. 어느 구현을 열어
봐도 비슷한 코드가 나옵니다. 인자 개수별로 직접 작성한 오버로드가 쌓여 있고,
대개 열 개나 스무 개 정도에서 끝납니다.

```ts
export function pipe<A, B>(a: A, ab: (a: A) => B): B;
export function pipe<A, B, C>(a: A, ab: (a: A) => B, bc: (b: B) => C): C;
// ...계속 이어진다
```

마지막 오버로드에 닿기 전까지는 잘 동작합니다. 하지만 그보다 한 단계 더 이어
붙이는 순간, 오류 메시지는 사용자의 프로그램이 아니라 라이브러리의 오버로드
목록을 이야기합니다. 누구의 잘못도 아닙니다. 라이브러리 작성자는 가능한 최선의
방법을 택했습니다. 한계 자체가 구조적입니다. 언어에 존재하지 않는 문법을 타입
시스템으로 표현하려는 것이고, 그 표현은 결국 실제 문법의 근사치일 수밖에
없습니다.

## 컴파일러는 알지만 말하지 않습니다

또 하나 마음에 걸렸던 것은 컴파일러의 침묵이었습니다.

```ts
type Shape =
  | { kind: "circle"; radius: number }
  | { kind: "rect"; width: number; height: number };

function area(shape: Shape) {
  switch (shape.kind) {
    case "circle":
      return Math.PI * shape.radius ** 2;
  }
}
```

TypeScript는 `shape.kind`가 정확히 `"circle" | "rect"`라는 사실을 압니다. 이
코드에서 `"rect"`가 처리되지 않았다는 사실도 압니다. 필요한 정보는 이미 타입
내로잉 결과 안에 있습니다. 하지만 먼저 묻지 않으면 알려 주지 않습니다. 그리고
묻기 위해서는 의례적인 코드를 작성해야 합니다. 값을 `never`에 대입하는 `default`
분기를 넣거나, 명시적인 반환 타입과 적절한 컴파일러 옵션을 사용해야 합니다. 같은
`case`를 두 번 작성해도 컴파일러는 아무 말이 없으며, 이를 발견하는 일은 린트
규칙에 맡겨집니다.

TypeScript가 감당해야 하는 모든 조건을 생각하면 이는 불합리한 선택이 아닙니다.
다만 태그드 유니언을 지원하는 대부분의 언어에서는 이런 검사가 언어 자체의
기능입니다. TypeScript에서는 개발자가 잊지 않고 작성해야 하는 관용구입니다. 타입
시스템이 이미 아는 사실을 말하게 만들기 위한 또 하나의 타입 장치인 셈입니다.

## 내가 정말 원했던 것

제품의 요구사항은 계속 복잡해지고 코드도 그에 따라 복잡해집니다. 함수 하나를 더
이상 머릿속에 온전히 담을 수 없을 만큼 커졌을 때 도움이 되는 것은 의외로
단순합니다. 무엇이 들어오고 무엇이 나가는지 정확히 아는 것, 코드가 실행되기 전에
가능한 한 많은 실수를 발견하는 것, 그리고 그 모든 내용을 몇 화면에 걸친 형식적인
코드 없이 표현하는 것입니다.

동기는 그것뿐이었습니다. 저는 이 세 가지를 TypeScript 안에서 얻고 싶었습니다.
타입을 더욱 교묘하게 만드는 대신, 그 작업을 한 단계 앞선 컴파일 과정으로 옮기고
싶었습니다.

## 이미 존재하는 언어를 선택하지 않은 이유

ReScript 같은 언어는 이미 이 문제를 훌륭하게 해결했습니다. 하지만 자체 문법을
JavaScript로 컴파일하는 방식으로 해결했고, 바로 그 지점이 장벽이 됩니다. 기능
하나를 도입하는 데 그치지 않고, 적어도 경계에서는 기존 생태계 밖으로 나가야
합니다. 이미 사용 중인 패키지의 타입, 에디터 도구, 팀이 지난해 작성한 코드,
앞으로 합류할 개발자까지 모두 영향을 받습니다. TypeScript 코드가 많이 쌓인
프로젝트에서는 언어가 아무리 좋아도 이러한 교환을 정당화하기 어렵습니다.

그사이 TypeScript는 선택적인 계층이 아니게 되었습니다. Bun은 TypeScript를 직접
실행하고 Node에는 타입 제거 기능이 있으며, 타입 중심 API가 일반적인 방식이
되었습니다. TypeScript는 JavaScript의 상위 집합이고, 이제는 생태계에서 사실상
선택하지 않기 어려운 부분이 되었습니다.

그래서 저는 반대 방향으로 갔습니다. tt는 TypeScript의 상위 집합이며 JavaScript가
아니라 *TypeScript로* 컴파일됩니다. TypeScript는 계속 컴파일 대상이자 타입
검사기로 남고, 프로젝트의 다른 모든 도구가 이미 이해하는 언어로 남습니다.

## 모든 설계가 기대는 단 하나의 원칙

**모든 유효한 TypeScript 파일은 유효한 tt 파일이다.**

컴파일러는 자신이 소유한 문법만 변환하고 나머지는 바이트 단위 그대로
통과시킵니다. 생성되는 결과는 `kind`로 태그된 유니언, `switch` 문, 일반 함수로
이루어진 평범한 TypeScript입니다. 런타임 라이브러리도, 타입 트릭도 없습니다.
tt가 보고할 내용이 있다면 파일·행·열과 함께 직접 알립니다.

이 원칙에는 두 가지 장점이 있습니다. 첫째, tt를 배운다는 것은 새로운 언어 전체가
아니라 몇 개의 키워드를 배우는 일입니다. 둘째, 마이그레이션 자체가 하나의
프로젝트가 될 필요가 없습니다. 파일 이름만 바꾸면 그대로 컴파일됩니다. `.tt`와
`.ts`는 서로를 양방향으로 import할 수 있으므로 아예 마이그레이션하지 않아도
됩니다. 상태 머신이나 파서, 결제 흐름처럼 중요한 부분만 tt로 작성한 뒤 기존
TypeScript 코드에서 사용하면 됩니다.

앞서 본 `switch` 문을 tt로 작성하면 다음과 같습니다.

```tt
enum Shape {
  Circle(radius: number),
  Rect(width: number, height: number),
}

const area = (shape: Shape): number =>
  match (shape) {
    Circle(radius) => Math.PI * radius ** 2,
  };
```

```text
error[match-not-exhaustive]: match on enum Shape is not exhaustive: missing "Rect"
 --> shape.tt:7:3
  |
7 |   match (shape) {
  |   ^^^^^^^^^^^^^
  |
  = help: add the missing arms
  |     Rect(width, height) => undefined,
  = help: or add a final `_` arm: `_ => undefined,`
```

`Circle`을 두 번 작성하면 `match: duplicate arm "Circle"`이라는 오류가
발생합니다. 타입 시스템이 처음부터 가지고 있던 정보를 이제 컴파일러가 명확하게
말해 주는 것입니다.

## 시그니처만 봐도 알 수 있는 오류

나머지 절반은 실패 처리입니다. tt는 오류를 던지기보다 반환하는 방식을 활용하면서,
개발자가 흔히 그 방식을 포기하게 만드는 불편함을 문법으로 해결합니다.

```tt
const loadProfile = (id: string): TResult<Profile, DbError | HttpError> =>
  result {
    const user <- findUser(id);
    const company <- fetchCompany(user.companyId);
    { user, company }
  };
```

각 `<-`는 성공 값을 꺼내고, 실패하면 그 실패를 즉시 반환합니다. 연산을 이어 갈수록
오류 타입은 자동으로 유니언으로 합쳐집니다. 성공 경로처럼 읽히는 이유는 실제로
성공 경로이기 때문입니다. 실패 가능성은 주석이나 호출 스택 몇 단계 위의 `catch`가
아니라 함수 시그니처에 드러납니다.

tt가 예외 던지기를 금지하는 것은 아닙니다. 여전히 TypeScript이므로 필요할 때는
그대로 `throw`를 사용할 수 있습니다. 다만 오류를 반환하는 방식도 실제로 편하게
사용할 수 있도록 만들어 줍니다.

## 예상하지 못했던 중요한 부분

이제 많은 코드가 AI와 함께 작성됩니다. 그 과정이 잘 풀리는지를 결정하는 것은
컨텍스트입니다. 단순히 컨텍스트가 "충분히 많은가"가 아니라, 모델이 실제로 볼 수
있는 창 안에 *올바른* 컨텍스트가 들어 있는가가 중요합니다.

그런데 이는 제가 제 자신을 위해 원했던 성질과 같았습니다. `match` 안에는 가능한
케이스의 전체 목록이 바로 드러납니다. `TResult<Profile, DbError | HttpError>`를
반환하는 시그니처에는 가능한 실패의 전체 목록이 바로 드러납니다. 그 정보는 다른
파일이나 몇 단계 아래에서 발생하는 `throw`, 또는 누군가 회의에서 설명한 관례 속에
숨어 있지 않습니다. 모델이 tt 코드 마흔 줄을 읽으면 그 마흔 줄이 무엇을 하는지
설명할 수 있습니다. 밤 11시에 코드를 검토하는 사람도 마찬가지입니다.

## 지금 tt는 어디까지 왔나

tt는 아직 초기 단계입니다. 컴파일러는 Rust로 작성되어 있습니다. 언어가 추가하는
것은 일곱 가지 구문과 하나의 바인딩 수식자뿐입니다. `enum`, `match`, `try`,
`let-else`, `if let`, `|>`와 `flow`, `result` 블록, 그리고 `val`입니다. 아직
프로덕션 사용을 권할 단계는 아닙니다.

하지만 그 모습은 제가 원했던 것과 같습니다. 기존의 것을 포기하지 않고, 새로 배울
것은 몇 가지뿐이며, 컴파일러는 타입이 이미 알고 있던 사실을 분명하게 말해
줍니다.
